# workflow
- Wants the todo list kept visible/present throughout a working session — not just shown once and then hidden; expects persistent task visibility while working. Confidence: 0.65
- Prefers referencing file paths rather than pasting document contents into the prompt, to conserve context window. Uses canonical roadmap/status documents as the source of truth across sessions. Confidence: 0.55
- After each verified milestone completes, update the canonical roadmap and docs/implementation-status-urdu.md with actual implementation status, evidence, remaining gaps, and next priority — keeping the documents in sync with reality, not aspirational. Confidence: 0.70
- When a customer demo is imminent and time is tight, reprioritize to visible UX/presentation quality over backend infrastructure work — the user will explicitly redirect from persistence/plumbing toward demo-critical paths. Confidence: 0.70
- Before implementing any non-trivial feature, enter plan mode, read canonical roadmap/status documents, inspect live repository code, write a concrete implementation plan, and get plan approval — then track work with todo_write milestones. Never start coding before the plan is approved. Confidence: 0.95
- When the full test suite reveals a pre-existing regression or stale assertion, fix it before declaring the milestone complete — don't ship a red build even if the failure predates the current work. Confidence: 0.70
- Before major UI redesigns, create or update a design brief (`.commandcode/design/brief.md`) grounded in existing product evidence and audit reports — let the brief define the register, audience, composition patterns, anti-references, and visual foundation before touching XAML. Confidence: 0.75
- When executing a design system change, rebuild shared resources (palette, radii, shadows, typography tokens) first, then rewrite each page XAML in a consistent pass — rather than incrementally adjusting individual pages. Confidence: 0.70
- For large XAML redesigns, use write_file to replace entire page files rather than iterative edit_file calls — the surface changes are holistic, and piecewise edits create mismatched intermediate states. Confidence: 0.65
- When running multiple `dotnet test` commands that target the same MAUI project, run them sequentially — parallel test processes collide on shared `input.json` and intermediate output files, causing spurious build failures. Confidence: 0.65
- When a clarification, expansion, or refinement to the plan emerges during discussion, update the plan file to incorporate it before exiting plan mode — the written plan should be the single source of truth when implementation begins. Confidence: 0.60
- When the user presents a standing-goal list with mixed done/not-done items and asks what's remaining, present a concise gap analysis first (what's done, what's in-flight, what's genuinely missing) before launching into planning — don't jump straight to a full-detail plan without first giving the user a clear snapshot. Confidence: 0.70
